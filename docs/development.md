# Deskpass development guide

For people who build or change Deskpass. Using it is covered in the [user guide](user-guide.zh-TW.md) (Traditional Chinese); the project overview is in the [README](../README.md); how to contribute is in [CONTRIBUTING](../CONTRIBUTING.md); security reports go through [SECURITY](../SECURITY.md). Domain terms (background delivery, foreground restore, foreground delivery, `background_unavailable`) are defined in [CONTEXT](../CONTEXT.md); the decisions behind the design are the ADRs:

- [0001: UI Automation actions use background delivery, and refuse explicitly when that is impossible](adr/0001-uia-actions-background-delivery.md)
- [0002: background delivery by foreground restore](adr/0002-background-delivery-by-foreground-restore.md)
- [0003: the public history starts at one commit](adr/0003-public-history-starts-at-one-commit.md)

Deskpass is a computer use MCP server for Windows. The policy (approval, risk tiers, the single-operator lock, the stop keys, coordinate scaling) lives in the Node.js server; the actual Win32 work is done by the bundled Rust helper.

It runs on Windows 10 1903 (build 18362) or newer, but only 2004 and newer is supported: Windows Graphics Capture is required. The display-affinity API that keeps the border out of screenshots needs Windows 10 2004; on 1903 to 1909 Deskpass still operates, but the border can appear in screenshots. Screenshots (zoom included) are taken without the mouse cursor on Windows 10 2004 and newer; older systems still capture the cursor.

## Build

Requirements: Node.js 22 or newer, and Rust stable with the MSVC toolchain (which needs the Visual Studio C++ build tools). See [CONTRIBUTING](../CONTRIBUTING.md) for the full setup.

```powershell
npm install
npm run build
```

`npm run build` runs `build:helper` (`cargo build --release`), then `build:ts` (`tsc`), then copies the helper into `dist`. Afterwards the server entry is `dist/index.js`, the helper is `dist/deskpass-helper.exe` next to it, and the build id is recorded in `dist/helper-build.json`. The server looks for the helper in this order: an exe in the same folder as the running script, `dist/deskpass-helper.exe`, `helper/target/release`, `helper/target/debug`. When the build id the helper reports does not match `helper-build.json`, the server does not use it, and the error tells you to rebuild with `npm run build`.

Commands:

- `node dist/index.js`: the MCP server (stdio).
- `node dist/index.js settings`: the settings page.
- `node dist/index.js panel`: the native control panel is gone; this command only writes a one-line pointer to stderr and exits with 0. The line follows the interface language (see "Interface language" below): in English it is "The control panel is now the settings page: run deskpass settings".

## Registering with Claude Code (for development)

After building in this project folder, register it with one command:

```powershell
claude mcp add --transport stdio deskpass -- node "<path>\dist\index.js"
```

`<path>` is the full path of this project folder; quote it when it contains spaces. The server name is `deskpass`, so the model sees tools with the prefix `mcp__deskpass__`. The transport is stdio, started as `node` with the server entry as its only argument. Any other MCP client uses the same `node dist/index.js` as its stdio command. The packaged `install.ps1` runs the same line with `--scope user`, pointing at `%LOCALAPPDATA%\Programs\Deskpass\dist\index.js`, and also prints the MCP server definition for other clients (see "Packaging").

## Interface language

There are two languages, Traditional Chinese (`zh-TW`) and English (`en`). The rule is in `src/ui-language.ts` (`decideUiLanguage`): `DESKPASS_LANG` wins when it is exactly `en` or `zh-TW` (case-sensitive; any other value is ignored); otherwise the first of the Windows UI languages decides (`HKCU\Control Panel\Desktop\PreferredUILanguages`, else `HKCU\Control Panel\Desktop\MuiCached\MachinePreferredUILanguages`, read with `reg.exe`): `zh-TW`, `zh-HK`, `zh-MO` and any `zh-Hant` tag give `zh-TW`, everything else, or a failed lookup, gives `en`. Each server decides once when it starts (the MCP server, and separately the settings server), keeps the answer, and passes it to every helper it starts as `--lang <en|zh-TW>`; the helper never detects a language, and without `--lang` its texts are English. `install.ps1` and `uninstall.ps1` are separate PowerShell processes that repeat the same rule; the comment above their `Get-DeskpassLanguage` says to change them together with `src/ui-language.ts`.

Not translated: tool descriptions and error codes (they are for the model, in English), log field names, app names and paths.

| `computer_zoom` | Enlarges a region of a screenshot. Later coordinates still refer to the ordinary screenshot. |
| `computer_click` | Clicks at screenshot coordinates (`x`, `y`) or on a UI-tree element (`element_index`, by default from the window's newest tree, `tree_id` picks another): the element's position is re-read at click time and the center of its visible part is clicked. An app that does not respond within 3 seconds gives `input_failed`: if it hung during the write the app may still apply it later; if it hung before the write, the message says nothing was written and nothing will be. |
| `computer_element_action` | Performs `action` on an element by UI-tree index (`element_index`, `tree_id` as for click) through UI Automation, without the mouse: `invoke` (press a button or menu item), `toggle` (check box), `expand`/`collapse` (combo box, tree item, menu), `select` (list item, tab, radio button), `scroll_into_view`, `focus` (put keyboard focus on it). An `action` outside these seven returns `invalid_params` without asking. Uses the approval of the same app; optional `delivery_mode`, default `background` (see "Background delivery and `delivery_mode`"; `focus` returns `background_unavailable` in the background); with `foreground`, every action (`scroll_into_view` and `focus` included) is brought to the front with the overlay before it runs, and a stop key can stop it. A password field only accepts `focus`; any other action returns `password_field` (see "Password fields"). An app that does not respond within 3 seconds gives `input_failed`: if it hung inside the action the app may still perform it later; if it hung before the action the message says it was not performed and will not be; if the action finished and only the read-back hung, the message says the action was done and must not be repeated. `scroll_into_view` does not scroll a partly visible Win32 list box row any further (Windows counts it as visible). |

| `computer_paste_text` | Pastes text into a window through the clipboard (at most 20,000 characters); good for long text or text an input method might change. The result says whether the target read it back (`read_confirmed`) and how the clipboard was restored (`clipboard_restored`). |
| `computer_press_key` | Presses a key combination such as `ctrl+s`. The modifier keys are read by the target before the main key is sent (UWP apps wait for a response instead); one call takes at most 5 seconds. |
| `computer_scroll` | Scrolls. `amount` is an integer from 1 to 50, default 3. |
| `computer_drag` | Drags. With `modifiers`, they are held for the whole drag. |
| `computer_move_mouse` | Only moves the cursor. |
| `computer_wait` | Waits 0.1 to 10 seconds. Needs no approval and is not affected by the lock. |
| `computer_list_apps` | Lists installed desktop and UWP apps (running or not, most recently used first, at most 200), each with an `app_id` that `computer_launch_app` accepts; apps in the blocked tier are marked `blocked`. Needs no approval. |
| `computer_read_clipboard` | Reads the text on the clipboard (only Unicode text, `CF_UNICODETEXT`; no images or file lists), at most 20,000 characters (counted in Unicode characters, never splitting one); longer text is truncated and the result says how many there were. There are 19 tools. Coordinates are image pixels of the most recent screenshot of that window. Coordinates outside the image send no input.

The action tools (`computer_click`, `computer_drag`, `computer_scroll`, `computer_move_mouse`, `computer_type_text`, `computer_paste_text`, `computer_press_key`, `computer_set_value`, `computer_element_action`, `computer_activate_window`, `computer_launch_app`, `computer_read_clipboard`) and every step of `computer_batch` accept an optional `action_summary`: what this step does and to what, without reasons, passwords or typed content. At most 200 characters (longer is truncated), line breaks and control characters removed. It is only written to the log; it does not appear in the approval question and does not affect approval; a call without it runs as usual.

## Background delivery and `delivery_mode`

Terms are in [CONTEXT](../CONTEXT.md); the reasoning is in [ADR 0002](adr/0002-background-delivery-by-foreground-restore.md). Background delivery means that when the action ends, the user's foreground window, window stacking order and cursor are the same as before it, and no keyboard input was sent to the window the user is working in.

- **Parameter**: optional `delivery_mode`, `"background"` or `"foreground"`; any other value returns `invalid_params`. It exists on `computer_click`, `computer_element_action`, `computer_set_value`, `computer_type_text`, `computer_press_key`, `computer_scroll`, `computer_drag` and `computer_paste_text`, and each step of `computer_batch` may carry it too (the default is the same as for a single call). It affects only that call.
- **Default**: `computer_element_action`, `computer_set_value` and `computer_click` (with `element_index` or `x`/`y`) default to `background`; every other tool defaults to `foreground`. `foreground` is the behavior from before background delivery existed: bring to front, overlay, and all the checks listed under "Keeping input away from other apps".
- **Background path**: UI Automation only. No foregrounding, no cursor movement, no change of stacking order (foreground restore excepted), no `SendInput` (except the zero-movement mouse move sent when a foreground restore is refused). Before anything is sent the stop state, approval, `expected_app`, administrator windows, minimized windows and dialogs are still checked; dialog detection does not look at who is in the foreground (an owned window with `WS_EX_NOACTIVATE` is not a dialog), and a dialog returns `dialog_open`.
- **How a click maps**: a plain left click with no modifier tries Invoke, Toggle, SelectionItem Select and ExpandCollapse in that order and uses the first one supported. With `x`/`y`, the helper looks in the target window's own UI tree for the deepest element that contains the point and has any of these patterns; it does not use the on-screen hit test, so windows covering the target do not matter and the action cannot land on another app.
- **`background_unavailable`**: the error code returned when the background cannot do it. The message suggests `Retry this action with delivery_mode: "foreground"`, and the data carries `reason` and `recommended: "foreground"`. Nothing is sent, nothing is brought to the front, no border is shown. Deskpass does not switch to the foreground by itself and asks the user nothing more. The `reason` values:
  - `needs_pointer`: right click, double click, a click with modifiers.
  - `no_click_pattern`: the element supports none of the patterns above.
  - `no_element_at_point`: no actionable element at the point in the target's UI tree.
  - `focus_needs_foreground`: the `focus` element action.
  - `minimized`: the target is minimized.
  - `tool_needs_foreground`: the tool has no background path; a foreground-only tool given an explicit `"background"` returns this too.
- **The switch**: "Allow background operation" in the settings page is stored as `allow_background` in `%LOCALAPPDATA%\deskpass\settings.json` (at most 64 KB is read), default `true` (a missing file, a missing key or a non-boolean value counts as on); the server reads it on every call, so a change takes effect on the next call. When it is off, every action that did not explicitly ask for the foreground runs as `foreground`, and the result gets one more line: "The user turned off background operation, so this action was done in the foreground." (`BACKGROUND_OFF_NOTE` in `src/delivery.ts`). `computer_batch` reads the switch once before it starts; a change during the run does not affect the remaining steps.
- **Waiting for the user to stop**: each background action, after its checks pass and before UI Automation is called, waits until the last physical keyboard input is more than 300 ms old and no physical mouse button is held, for at most 3 seconds; after that it runs anyway. Only physical input counts (the low-level hooks exclude events with the injected flag). The stop state is still checked during the wait, and a stop returns `stopped_by_user`. The result and the log carry `waited_for_idle_ms` (0 when it did not wait), and `idle_wait_capped: true` when the full 3 seconds elapsed.
- **Foreground restore**: from the start of the action until 500 ms after it returns, the helper watches the foreground (`EVENT_SYSTEM_FOREGROUND`, plus a read of `GetForegroundWindow` every 1 ms). When the new foreground belongs to the target's process, or its root window is the target (for example UWP's `ApplicationFrameHost`), it immediately calls `SetForegroundWindow` to give the user's original window back; a foreground that belongs to another process is not restored. When refused, it first sends a relative mouse move with dx=dy=0 and calls again, up to 3 times, 5 ms apart, without `AttachThreadInput`. Then, with `SWP_ASYNCWINDOWPOS`, it puts the target back directly below the window that was directly above it before the action, and the result waits up to 1 more second until the target really is there.
- **Restore results**: when the foreground was taken and given back, the result carries `foreground_restored: true`. When the foreground still belongs to the target, or is empty, at the end of the watch, the action still counts as done and returns `foreground_changed` with `restore_failed: true`; there is no retry.
- **Log**: `tool_call` events carry these extra fields: `delivery` (`background` or `foreground`), `reason` when refused, `foreground_restored` or `restore_failed`, `waited_for_idle_ms` and `idle_wait_capped`. The settings page's log marks each row "Background" or "Foreground" by `delivery`, and a refused background action is marked as background operation unavailable.
- **Overlay**: during background delivery the border is cut with a window region to "the target's outline minus the other visible top-level windows above it", updated when the visible part changes, and not drawn when it is fully covered. The corner notice is a separate window (no focus, click-through, topmost, `WDA_EXCLUDEFROMCAPTURE`) in the lower right of the work area of the screen the target is on; it appears and disappears together with the border. The text comes from `overlay_show`'s `app_name` and `delivery_mode`: for background "AI is operating ‹app› · Ctrl+Alt+Esc to stop", for foreground "AI is operating ‹app› · Esc to stop"; the border label is "AI is operating · press Ctrl+Alt+Esc to stop" or "AI is operating · press Esc to stop". Read-only tools (screenshot, UI tree, zoom) carry no delivery mode and keep the one currently shown, or use the background text when nothing is shown. The texts are in `helper/src/strings.rs`, one table per language.

## Log

Every tool call (and every step of `computer_batch`, as its own entry) writes one `tool_call` line to `%LOCALAPPDATA%\deskpass\logs\YYYY-MM-DD.jsonl`: `time`, `session` (a random id made when the server starts), `tool`, `step` (the 1-based number inside a batch, otherwise `null`), `app` (`{ path, key, tier }`, `null` when there is no app; `tier` is `blocked`, `high` or `normal`, see "Approval, risk tiers and the lock"), `action_summary`, `result` (`ok` or an error code), `duration_ms`.

`app.key` is the app's identity key: for a packaged app (UWP / MSIX) `package:` plus the lower-case package family name; for an app with a valid Authenticode signature `signer:` plus the signer (the full subject of the leaf certificate), `|`, and the lower-case file name; for everything else (unsigned, failed verification, or no identity available) the lower-case, backslash full path. Signatures are verified with WinVerifyTrust against the certificate chain, system catalog signatures included; revocation is not checked and nothing goes over the network, so a revoked certificate is not recognized. Identities are cached by path and modification time.

Other events:

- `approval`, one per approval decision: `time`, `session`, `app`, `channel` (`elicitation`, `dialog`, `session` for an allow or refusal remembered in this session, `grant` for an always-allow in the grants file; `null` for blocked apps, which are not asked), `answer` (`allow_once`, `allow_always`, `refuse`, `timeout`, `unavailable`, `refused_earlier`, `blocked`).
- `grant_invalid`, one per entry of the grants file (see "Grants file") that did not count each time it is read: `entry` (`grant`, `raised`, or `file` for the whole file), `key` (the entry's app identity key, at most 300 characters, `null` if none), `reason`: `malformed` (wrong fields or no MAC), `bad_mac` (MAC mismatch), `not_signed` (an always-allow for an unsigned app), `not_higher` (a raise that does not exceed the built-in tier), `unreadable` (the file cannot be read as a grants file, or exceeds 1 MB), `rollback` (the file's `generation` is lower than the server has accepted). For `entry: file`, `bad_mac` means `file_mac` does not match (entries were added, removed or reordered) and `not_signed` means the file has no `file_mac`. The same file content is logged once.
- `grant_key_lost` (`entries`: the number of entries that became invalid), when the key cannot be decrypted.
- `grant_mismatch`, when an always-allow no longer matches the app's current identity (see "Identity mismatch" under "Grants file").
- `clipboard_read`, for `computer_read_clipboard`: `chars` (the number of characters returned) and `truncated`; never the content. Its approval event has `app` set to `null` and `subject: "clipboard"`.
- Changes made on the settings page, with `session` set to `settings` (see "Settings page (technical)").

The log never records typed or pasted text, key presses, clipboard content, screenshots, element-tree content or window titles. At server start and at the first write of each day, files older than 30 days are deleted; when the total size exceeds 10 MB, the oldest files are deleted first (today's file never). A failed write does not affect the tool; it is reported once on stderr.

## Keeping input away from other apps

This section is the checks for foreground delivery (`delivery_mode: "foreground"`); the checks for background delivery are under "Background delivery and `delivery_mode`". Before every foreground input tool sends anything it confirms the following, and when any fails nothing is sent and an error is returned:

- The target is in the foreground. If foregrounding fails the call returns `input_failed` and the window stacking order is restored.
- The target has no open dialog. Otherwise `dialog_open` is returned, with the dialog's `window_id` and title; the dialog itself can be operated as usual.
- The point to click is not covered by another app (a picture-in-picture window, a call bar, a sticky note). A covered point returns `target_obscured`, and the message says which app's window covers it; when the covering window is not topmost it suggests running `computer_activate_window` on the target and retrying, when it is topmost it suggests operating an uncovered part or asking the user to move it. Both the start and the end of a drag are checked. Right-click menus, drop-down lists and tooltips opened by the target app itself (same UI thread) do not count as covering: they appear in the screenshot, and the parts beyond the target window can be clicked.
- The point is on some screen. When part of a window lies outside every screen, a point sent there would be clamped by Windows to the nearest screen edge and land elsewhere in the window or in another window, so it is not sent and `offscreen` is returned, asking the model to use the part inside a screen or the user to move the window back. The `on screen:` line of the screenshot lists the image ranges that are on a screen; the start of a drag and every segment point are checked.

During the input the foreground is checked again before every click, every drag segment, every scroll notch, every key and every character. If the target loses the foreground midway, or is closed by an Enter in the text, the remaining input is not sent (buttons and keys already pressed are released as usual), and the call returns `input_failed` saying how much was sent.

If the target gives up the foreground only after all the input was sent (for example a click opens a new window, or an Enter closes a dialog), or another app takes the foreground, it still counts as success: the message says which window is now in the foreground (`window_id`, title, app) or that the target was closed, and asks the model to take a screenshot of that window before continuing rather than repeat the input. If the foreground is another app, the message states that the input went to the target, not to that app.

Typing and key presses wait until the target really reads the input before reporting success, so the speed follows the target, about 12 to 15 ms per character. `type_text` stops after 20 seconds and returns `input_failed` with the number of characters typed; the rest needs another call. A target that does not read input for 5 seconds also gives `input_failed`.

UWP apps (Calculator, Settings, ...) are the exception: Windows does not let the helper follow their input queue, so it cannot confirm that a key was read. For these apps the foreground and the stop state are still checked before every character or key, and after sending, the helper waits for the app to respond twice in a row before sending the next; no response for 5 seconds returns `input_failed` ("did not respond") with the number sent. The success message adds a request to the model to confirm with a screenshot, and the helper result carries `read_confirmed: false`. `type_text` first asks the app to switch to the English keyboard layout; if the app does not switch, it types in the existing layout, the result carries `layout_switched: false`, and the message adds a reminder that the input method may compose or hold the characters and that the screenshot should be checked for missing or changed characters.

In a window with a Chinese input method open: `press_key` turns the input method off for the duration of the key; `type_text` switches to the English layout for non-ASCII text (for UWP apps always, whatever the text). When it finishes, on success, error, interruption or a closed target, the input method and keyboard layout are restored.

## Password fields

When the focus is in a password field (for `computer_set_value` and `computer_element_action` the target element is checked instead), every tool that would send content is refused with `password_field`, and no input is sent (in a batch, that step has `sent: false` and the batch stops there); the message asks the model to let the user type it. After approval and before the first input is sent, the helper reads the element's IsPassword through UI Automation. This applies to every risk tier.

- `computer_type_text`, `computer_paste_text`, `computer_set_value`: refused.
- `computer_element_action`: when the target element is a password field only `focus` runs (putting the focus into the field so the user can type); every other action is refused (for when IsPassword cannot be read, see the known limitation below). Once the focus is there, `computer_type_text`, `computer_paste_text` and `computer_set_value` are still refused by the rules above.
- `computer_press_key`: only keys that produce characters and paste keys are blocked: letters, digits, a plain Space, those with Shift or with Ctrl+Alt (many keyboard layouts produce characters with AltGr), and Ctrl+V, Win+V (clipboard history) and Shift+Insert (whatever else is held). Other keys are sent as usual so the focus can leave the field: Tab, Enter, Esc, the arrow keys, Home, End, Page Up/Down, Backspace, Delete, F1 to F24, and shortcuts such as Ctrl or Alt with a letter (for example Ctrl+A) or Win with a key other than V.
- When the text of `computer_type_text` contains a Tab or a line break (Enter), the focus is checked again after the target has read that character; if the focus moved into a password field it stops there and returns `password_field`. That step counts as having sent input (`sent: true` in a batch), and the message says how many characters were typed and that the rest was not sent.

Known limitation: when UI Automation cannot be read (the app has no provider, does not respond within 1 second, or IsPassword cannot be read) the input proceeds and the field is not treated as a password field. During the input the check is repeated only after a Tab or a line break: when the app moves the focus into a password field after some other character (for example auto-advancing after a number of characters), the characters after that are still sent. For UWP apps, "this character has been read" is an estimate, so if the app moves the focus asynchronously a little later, the re-check can come too early.

## Approval, risk tiers and the lock

The first time an app is operated, the server asks the user whether it may be used. An allow is kept only in the memory of this session; always-allow is described under "Grants file". Session allows and refusals are keyed by the app's identity key (see "Log"), so the same executable from the same signer at a different path is the same app; a refusal is also remembered by path, so when the app's identity cannot be read later (that time keyed by the path) it still counts as refused. A refusal the user pressed (the dialog's "Deny", Esc or close, or the client's Decline or cancel) is remembered in this session too: when the model asks for the same app again it gets `approval_refused_earlier` at once and the user is not asked again; restarting the MCP server clears it. No answer (timeout) and not being able to ask (`approval_unavailable`) are not remembered, so the next call asks again.

A UWP app's window belongs to the frame process `ApplicationFrameHost.exe`. The question, the approval and the risk tier all follow the app inside the frame (for example `CalculatorApp.exe`), so allowing Calculator does not allow other UWP apps such as Settings. When the app inside the frame cannot be identified (it has just started or is suspended), operation is refused with `app_unresolved` and nobody is asked; waiting a moment and calling `computer_list_windows` again is enough.

Before every action the helper confirms again that the window still belongs to the approved app; when it has become another app (for example the window was closed and the same handle was reused by another app) it returns `app_changed` and sends nothing. If the window changes app while the approval is being asked, the new app is asked about separately.

An app that can be always-allowed (normal tier, with a `signer:` signature or a packaged `package:` app) is always asked through the helper's Windows dialog, even when the client supports elicitation, because the client's question cannot offer "Always allow"; when the dialog cannot be shown the call returns `approval_unavailable` and does not fall back to the client's question. Other apps (high tier, unsigned) are asked as before: through the client when it declares form elicitation, and through the helper's dialog when the client does not declare it or the question fails (for example a Claude Code background session that waited 60 seconds without an answer). Accept in the client's question is always only an allow for this session. The dialog shows the app name and the full path:

- The buttons are "Allow once" and "Deny"; an app that can be always-allowed also gets "Always allow".
- The dialog is topmost and takes the foreground. The default button and the initial focus are "Deny", so a lone Enter or Space refuses; allowing needs a mouse click. For 0.7 seconds after the dialog appears neither "Allow once" nor "Always allow" accepts a click, so a click meant for something else cannot hit it. Esc, Alt+F4 and the close button all refuse.
- With no answer within 60 seconds it closes by itself, counted as a refusal; the model gets `approval_declined` and is told the user did not answer. This refusal is not remembered.
- While the dialog is open the helper runs no other request (including input sent at the same time by the same session), and the server holds its own requests back too; the dialog belongs to the helper process, so it never appears in `computer_list_windows` and cannot be approved or operated. The model cannot answer for the user.
- When the screen is locked or there is no interactive desktop it cannot be shown, and every tool that needs approval is refused (`approval_unavailable`, the message says the user was not asked); the server writes the reason on stderr.

Risk tiers: every app is in one tier. Matching is by executable name (case-insensitive); UWP apps are also matched by package family name (currently read from the install folder `WindowsApps\<package>`). The single source of the built-in tiers is `BUILT_IN_TIERS` in `src/policy.ts` (each group also has a display name and reason in the string tables of the settings page); both the approval check and the settings page read it.

- **Blocked** (`blocked`): nobody is asked; the call returns `blocked_app` with a message saying that the app is in the blocked tier and why. The groups are: terminals (cmd, powershell, pwsh, powershell_ise, WindowsTerminal, wt, OpenConsole, conhost, wsl, bash, mintty, alacritty, wezterm, wezterm-gui, hyperkitty, warp, and the Store Windows Terminal and Preview with package families `microsoft.windowsterminal_8wekyb3d8bbwe` and `microsoft.windowsterminalpreview_8wekyb3d8bbwe`); Windows administration tools (regedit, mmc, taskmgr); the UAC consent prompt (consent); the Windows credential prompt (CredentialUIBroker); Deskpass itself (deskpass-helper and the old name computer-use-helper), and any process of this project's own helper or server.
- **High** (`high`): asked as usual, the allow lasts only for this server session, never always-allow. Browsers (msedge, chrome, firefox, brave, opera, vivaldi, iexplore); explorer (File Explorer); Settings and Control Panel (SystemSettings, control, package family `windows.immersivecontrolpanel_cw5n1h2txyewy`); password managers (1Password, Bitwarden, KeePass, KeePassXC, Dashlane, LastPass); mail (OUTLOOK, olk, Thunderbird, the UWP Mail `microsoft.windowscommunicationsapps_8wekyb3d8bbwe`, the new Outlook `microsoft.outlookforwindows_8wekyb3d8bbwe`).
- **Normal** (`normal`): every other app, asked as usual, the allow lasts for this server session.

Windows running as administrator, `app_unresolved`, and the `ApplicationFrameHost.exe` rule above are decided before the tier. `computer_launch_app` does not start `ApplicationFrameHost.exe` either (it only hosts the windows of UWP apps and is not an app itself) and returns `blocked_app` for it.

Only one Deskpass session may operate the computer at a time. The lock file is `%LOCALAPPDATA%\deskpass\session.lock` with the content `{ pid, startedAt, lastUsedAt }`. `lastUsedAt` is when the holder's last tool call ended, updated at the end of every call (written to a temporary file and renamed over the lock, so other sessions never read a half-written file); a lock file written by an older version has no such field and is still judged. A session holding the lock that makes no tool call for 2 minutes (counted from the end of its last call; a call in progress, `computer_batch` and `computer_wait` included, is never cut short) releases the lock by itself, finishing as it does on exit: it removes the overlay, ends the keyboard hook for the Esc stop, and deletes the lock file (only if it is still its own); the helper process stays. Its next call that needs the lock takes it again by the normal rules, and if another session holds it by then it gets `in_use`. While another live session holds the lock, a later call gets `in_use`, with the holder's PID, start time (local and ISO), how long ago its last tool call was, and that it releases the lock after 2 idle minutes, so the model can ask the user to try again later or close that session; a holder of an older version never releases the lock, and the message says it does not know the last time of use. When the holder's process has exited, or its PID was reused by another process, the lock is taken over. When the holder is alive but its start time cannot be read, the call returns `in_use` with the lock file's path; if you are sure no other AI session is operating, you can delete the file by hand. A lock file whose content cannot be parsed is not taken over for 5 seconds and is taken over after that.

A window running as administrator cannot be operated when the helper itself is not running as administrator.

## Reading the clipboard

The first time `computer_read_clipboard` is called in each server session, the helper asks through a Windows dialog whether the AI may read the text on the clipboard for this session. It has two buttons only, "Deny" and "Allow once"; always-allow does not exist. The dialog follows the same rules as the app approval dialog: the default and the initial focus are "Deny", "Allow once" does not accept a click for 0.7 seconds after it appears, Esc, Alt+F4 and the close button all refuse, and 60 seconds without an answer counts as a refusal.

- It is always a dialog, never an MCP elicitation, even when the client supports it; when the dialog cannot be shown the call returns `approval_unavailable`.
- An allow lasts for this server session; a refusal is remembered too, and later calls return `approval_refused_earlier` until the MCP server is restarted. No answer (`approval_declined`) and a dialog that could not be shown are not remembered; the next call asks again.
- The log records only how many characters were read (see "Log").

## Grants file

Always-allow entries and risk tiers the user raised are stored in `%LOCALAPPDATA%\deskpass\grants.json`: `{ version: 1, generation, grants: [{ key, display_name, path, created_at, last_used_at, mac }], raised: [{ key, tier, created_at, mac }], file_mac }`. `generation` is an integer that goes up by one on every write. `key` is the app's identity key (see "Log"); only signed apps (`signer:`) and packaged apps (`package:`) can be always-allowed, and an always-allow keyed by path does not count. An always-allow is added only by the user pressing "Always allow" in the approval dialog (the server accepts it only from that dialog answer; the client question's Accept and any parameter from the model cannot write one); revoking, raising and restoring the default are done on the settings page (see "Settings page (technical)"). Deleting or editing `grants.json` by hand voids every always-allow (the MACs no longer match, and the app is asked again). No MCP tool can write this file.

- **Signatures**: every entry's `mac` is an HMAC-SHA256 (64 lower-case hex characters) over the canonical JSON of all the entry's fields except `mac` (field names sorted alphabetically, no whitespace; every field is a string, and no other fields are allowed). `file_mac` signs the whole file: the canonical JSON of `{ version, generation, grant_macs, raised_macs }` (the last two are the entries' `mac` values in file order); it must exist whenever the file exists (even with no entries), and only a missing file has no signature. Canonicalization is done by the helper (the server passes the fields; the helper checks that they are complete and correctly typed, sorts them and writes serde_json's compact form: `"`, `\` and control characters escaped, U+2028 and characters outside the BMP written as they are in UTF-8), and the server and the settings server use the same one. The key is 32 random bytes, protected with Windows DPAPI (current user) and stored in `grants.key` in the same folder; the folder is decided only by Node (`%LOCALAPPDATA%\deskpass`, a temporary folder in tests), and both the server and the settings server pass it to the helper as the start argument `--grants-dir`; a helper without that argument refuses `grant_mac` and never looks for a folder itself. A request cannot name another file. Only the helper decrypts the key and computes the MACs (`grant_mac`); the server only receives MACs, and the key appears in no response, log or error message.
- **Verification**: an entry whose MAC does not match, whose fields are wrong, or that has no MAC (for example one added by editing the file) is ignored and logged as `grant_invalid`. A missing or mismatching `file_mac` (entries added, removed or reordered) voids the whole file and is logged as `grant_invalid` (`entry: file`). The server remembers the highest `generation` it has accepted (verified) during this run; a file that does not count never changes it; a lower one (for example an old copy put back, or the file deleted) voids the whole file and is logged as `rollback`. While the whole file is void there are no always-allows, and the raises verified last stay in force (they can only be stricter). A key that cannot be decrypted (DPAPI reports the data corrupt or not for this profile: the profile was reset, or the machine or user changed; or the data is not DPAPI data, does not decrypt to 32 bytes, or the file exceeds 4 KB), or a file with entries whose key is missing, voids every entry, is logged as `grant_key_lost`, and the helper creates a new key, after which apps are asked again. Other errors (the file is in use, no permission, other DPAPI errors) do not replace the key and are treated as the helper being unable to compute a MAC. A grants file that does not exist, is not JSON, has a version other than 1 or exceeds 1 MB is treated as having no grants at all (the last three are logged as `grant_invalid`), and tools proceed as usual. When the helper cannot compute MACs (an error or a timeout), this check uses no always-allow, the raises verified last stay in force, and the file is read again at the next check.
- **Taking effect**: on every approval check the server looks at the file's modification time and size, and when either changed it re-reads and re-verifies, with no restart needed.
- **Always allow**: pressing "Always allow" writes one entry (`created_at` is that moment; an older entry with the same identity key is replaced), and later servers allow the app directly without asking; when the write fails the app is allowed for this session only, and the server says so on stderr. A normal-tier app with a matching always-allow is allowed directly, and the `approval` event has `channel: grant`, `answer: allow_always`. A high-tier app does not use always-allows; a refusal the user pressed in this session still takes precedence. Use updates `last_used_at` (the file is written at most once a minute); it is inside the signed range, so the entry is re-signed. Characters in names and paths that cannot be encoded (a lone UTF-16 surrogate) are written as U+FFFD; an identity key with such a character is not written.
- **Identity mismatch**: an always-allow only looks at the identity key. When the app at the same path now has a different identity key from the always-allow's (for example the signer changed, or it is no longer signed), that always-allow is not used and the user is asked instead, and a `grant_mismatch` event is written at that moment: `key` (the always-allow's identity key), `current_key` (the current one), `path`. Comparison uses lower-case, backslash paths; apps with a different path are not a mismatch and are simply asked. The always-allow is not deleted automatically.
- **Raised tiers**: a `raised` entry's `tier` is `high` or `blocked` and only counts when it is higher than the built-in tier; an entry that asks to lower or keep the built-in tier is ignored and logged as `grant_invalid` (`not_higher`). An always-allow for a raised app does not count, and raising it also deletes the always-allow. The approval check, the check before `computer_launch_app` starts anything, and the `blocked` mark in `computer_list_apps` all use the same effective tier (the built-in tier, or a raise above it): an app raised to blocked is refused before it is started (`blocked_app`, not started, not asked) and marked `blocked` in the app list.
- **Writing**: the whole file is written to a temporary file in the same folder and renamed over `grants.json`, so a read always sees one complete write; entries whose MAC does not verify are dropped when writing, `generation` goes up by one and `file_mac` is computed again. When the write finds that the key is newly created, old entries are not re-signed with the new key; they all become invalid, as at read time.
- **Protection boundary**: it holds against actions through the computer use tools, and against editing the file directly (for example the model adding or changing entries with the client's file-writing tool). It does not hold against anything that can run arbitrary programs as the same Windows user (it can call DPAPI and decrypt the key); that privilege can do anything anyway and is outside what this system protects. `file_mac` makes deleting, adding or reordering entries visible, and `generation` lets the server recognize a swapped-back older version during one run. After a server restart the first file it reads has nothing to compare with, so an older version swapped in before the restart (a complete old file signed with the same key, for example one that puts back a revoked always-allow) is not recognized.

## Settings page (technical)

`node dist/index.js settings` starts the settings server (installed, this is the Start menu shortcut "Deskpass Settings", which runs `deskpass-settings.vbs` through `wscript.exe` to start the same command with a hidden window). It is a different process from the MCP server, does not take `session.lock`, and uses only Node's built-in http. The server is `src/settings-server.ts`, the page is `src/settings-page.ts`, all the interface text is in `src/settings-strings.ts` (one table per language: `SETTINGS_TEXT` for zh-TW and `SETTINGS_TEXT_EN`, including the built-in tiers' names and reasons and the words of the log rows), and `src/settings-log.ts` builds the log page's sentences from the `logRows` words of the table.

- **Access**: bound to `127.0.0.1` on a random port only. At start a one-time token is made (32 bytes, valid 120 seconds, used once) and the default browser is opened at `http://127.0.0.1:<port>/open?t=<token>`; it is exchanged for an HttpOnly, SameSite=Strict session cookie and redirected, so the address bar keeps no token. Every request has its `Host` checked; POST also has its `Origin` checked; a `Sec-Fetch-Site` header that is present and is not `same-origin` or `none` is refused; responses carry no cross-origin headers. A refusal does not say which check failed. Browser automation tools that navigate directly often send `Sec-Fetch-Site: cross-site` and are refused; that is expected.
- **Only one**: `settings.lock` in the data folder records the pid, the port and a start secret; on a second run, if the existing server is alive it asks it for a new token with the secret, opens a new tab and exits; if it is dead it clears the lock and starts its own.
- **Auto stop**: the page asks for status every 5 seconds and asks again at once when the tab returns to the foreground (a background tab's timers are slowed by browsers to about once a minute); when there has been no authenticated request for 3 minutes, no confirm window is open and no unused token exists, the server exits and clears the lock.
- **Helper**: the settings server starts helpers itself (the same JSON-lines protocol) to compute MACs (`grant_mac`), list the Start menu apps (`list_start_menu_apps`, in a helper process of its own) and show the confirm window (`confirm_change`, each confirmation in a helper process of its own). It does not write `session.lock`, does not install the Esc hook and does not show a border.
- **Tightening (written directly)**: `POST /api/raise {key, tier}` and `POST /api/revoke {key}`. `key` must be a row of the current list, a tier is accepted only if it is strictly higher than both the built-in tier and the current raise, and raising also deletes the app's always-allow.
- **Loosening (only opens the confirm window)**: `POST /api/restore {key}` writes nothing, answers 202 and asks the helper to open the confirm window (60 seconds; the default focus is "Cancel", and "Allow" accepts clicks only after 0.7 seconds). `GET /api/restore?id=` answers pending, allowed, cancelled, timeout, changed or failed; when the id has been replaced by a confirmation updated from another tab it answers superseded and the page reloads its state. `GET /api/apps` carries the confirmation in progress (`confirm`), so a refreshed page keeps waiting for the same confirmation and no second window opens. A raise that equals the built-in tier and so has no effect can also be cleared with "Restore default...". The raise is removed only when the helper answers `allow`, and only if, in the very read that writes, the raise is still the tier that was confirmed; otherwise the outcome is changed and nothing is written. Another loosening request while a confirmation is in progress returns 409 `confirm_busy`. The window text is decided by the server from its own list, and control and format characters are removed and the length limited before it is sent.
- **Stop keys and the confirm window**: the confirm window runs in a helper process of its own, started for that one confirmation, and that helper never starts a session, so it has no keyboard hook and Deskpass's stop keys are not intercepted there. What the keys do while it is open:
  - Esc, with the window focused, is the dialog's own cancel key (`IsDialogMessageW` maps it to the cancel command, `helper/src/ask.rs`): the answer is `cancel`, which changes nothing. Esc and Alt+F4 are also exempt from the stale-input rule that guards the "Allow" button, and they can only refuse.
  - Ctrl+Alt+Esc is not handled by that helper. If an MCP session's helper is running its stop hook (an AI session holds the lock), that hook stops the AI and swallows the Esc of the combination, so the confirm window does not see it and stays open; it closes only through "Cancel", Esc, close, or its 60-second timeout.
  - A single Esc while the AI operates in the foreground goes to both: the MCP helper's hook counts it as a stop (a single Esc is not swallowed) and the confirm window receives it as cancel.
  - A stop inside the confirm helper itself (its stop counter rising: the settings server it belongs to going away, or `debug_stop` in test builds) closes the window without allowing and ends the request with `interrupted`; the settings server treats `interrupted` exactly like `cancel` and writes nothing.
- **No API can add an always-allow or set a tier below the built-in tier**; those rules are checked on the server.
- **Log**: `GET /api/log/days` and `GET /api/log?day=YYYY-MM-DD[&app=key]`; the choices are today and the days among the last 7 that have a file.
- **How it writes**: it reuses `src/grants.ts` (the same module as the approval dialog's "Always allow"): verify, modify, `generation` plus one, re-sign, rename a temporary file over the file. A running MCP server sees the change at its next approval check. When the grants file does not count (`file_mac` mismatching or missing, unreadable as a grants file, key lost), the page only shows the reason and every write returns 409 `grants_void`, because overwriting with the part that can be verified could leave an app in a lower tier than the running server remembers. To start over, close the programs that use Deskpass (the AI client and the settings page) and delete `grants.json` by hand. After deleting or restoring (putting an older copy back) `grants.json`, restart the MCP server and the settings page: a running process remembers the highest `generation` it accepted and treats a lower file as a rollback.
- Every change writes one log line with `session` set to `settings`: `tier_raised` (`key`, `tier`, `grant_removed`), `grant_revoked` (`key`), `tier_raise_removed` (`key`). The log page words them as changes made on the settings page; events written by the old control panel (`session: panel`) are worded as made in the control panel.
- **App list and names**: the list holds only the apps in the grants file and those that appear in the last 7 days of the log, one row per app, told apart by identity key. An app that exists only in the Start menu and was never operated by the AI is not in the list, and `/api/raise`, `/api/revoke` and `/api/restore` called with its key return 409 `unknown_app`, like an unknown app. The Start menu is used only to give the apps in the list their names: its apps are merged by identity, uninstall and help shortcuts and the shell's own entries (for example "Run") are dropped, and an unsigned program's identity is the program path the entry points to (backslashes, lower-case).

## Stop keys (technical)

While an action runs, a topmost, click-through window that does not take the focus shows a border around the target, whose top label names the stop key for the delivery mode: in the background "AI is operating · press Ctrl+Alt+Esc to stop", in the foreground "AI is operating · press Esc to stop" (the zh-TW table of `helper/src/strings.rs` has the same two texts in Traditional Chinese). The corner notice in the lower right of the screen names the same key (see "Background delivery and `delivery_mode`"). The border and the corner notice disappear 10 seconds after the last action, when the session ends, or when a stop key is pressed.

The stop rules are in `helper/src/esc.rs`, judged in a low-level keyboard hook, and only physical keys (without the injected flag) count:

- **Ctrl+Alt+Esc**: a physical Esc press while both Ctrl and Alt are physically held is a stop at any time. The hook swallows that Esc (press, repeats and release) and passes it neither to Windows nor to any app, because Windows would take Ctrl+Alt+Esc as Alt+Esc and send the user's front window to the back.
- **Single Esc**: a stop only while a foreground operation is in progress, or while the border of the most recent foreground operation is still shown; at any other time it passes to the user's app like every other key, and is not swallowed.
- All other keys are never swallowed.

An Escape or Ctrl+Alt+Esc that the model asks to be sent does not count as a stop; only a key the user physically presses does.

After a stop key, the helper sends no more input; up to 1 or 2 characters that were sent but not yet read by the target may still appear. A background action that receives the stop during the wait for the user to stop returns `stopped_by_user` and does nothing. After the helper restarts because of a timeout or a crash, the stop keys work as before (the server starts the session again with `session_start`, which installs the hook).

The hook exists only between `session_start` and `session_end` of one helper: helpers that never start a session (the settings server's helpers, including the one that shows the confirm window) have no stop keys.

### Manual acceptance

A physical key cannot be reliably simulated as a non-injected key by a program, so this part is done by hand. Start the server with `DESKPASS_LANG=en` to see the English texts below.

1. Build and register the server, and start a model turn that operates windows.
2. Ask the model to do a foreground action (for example `computer_type_text`) in a window that is approved, not in the blocked tier, and not running as administrator. Confirm the window gets a border whose text is "AI is operating · press Esc to stop", and that the corner notice in the lower right says "AI is operating ‹app› · Esc to stop".
3. While the action is still running, press a single Esc on the keyboard. Do not ask the model to call `computer_press_key` with Escape instead.
4. Confirm the running action stops. The first line of its result is `interrupted`. The first line of the next tool that needs approval is `stopped_by_user`. Both messages tell the model not to call these tools again, to end the turn and to tell the user.
5. Confirm the border is hidden.
6. If the model calls a tool again, the client asks "You pressed Esc to stop Deskpass earlier. Let the AI continue?" (when the client cannot ask, the helper's Windows dialog "Deskpass: Continue?" asks). Choosing allow ("Continue" in the dialog) clears the stop and the action can go on. Choosing deny ("Don't continue"), giving no answer for 60 seconds, or being unable to ask all still return `stopped_by_user`. Esc while the dialog is open refuses: the dialog closes and does not allow.
7. Ask the model separately to send Escape to the test window. That must neither stop anything nor close the session.
8. A single Esc during background operation: wait until the border disappears (10 seconds after the last action), then ask the model to do a background action on the same window (for example `computer_element_action`, or `computer_click` with `element_index`). Confirm the border text is "AI is operating · press Ctrl+Alt+Esc to stop" and the corner notice is "AI is operating ‹app› · Ctrl+Alt+Esc to stop". While the border is still shown, press a single Esc in another window: the AI does not stop, the next tool call runs as usual, and that window receives the Esc.
9. Ctrl+Alt+Esc: press it while the border of a background action is still shown. Confirm the first line of the next tool that needs approval is `stopped_by_user`, the border is hidden, and your front window was not pushed to the back. Then continue as in step 6 to confirm it can resume.

## Technical limits

- Windows running as administrator cannot be operated, and the helper does not raise its own privileges.
- UI Automation currently reads the tree (`computer_get_ui_tree`), clicks by index (`computer_click` with `element_index`), sets values directly (`computer_set_value`) and performs other element actions (`computer_element_action`).
- There is no whole-desktop mode, no holding a key down, and no macOS or Linux.
- Apps in the blocked tier (terminals, system administration tools, the UAC consent and credential prompts) cannot be started or operated through this server.
- Typing and key presses follow the target's speed and are slower than sending everything at once; long text has to be split over several `computer_type_text` calls.
- Clicks and drags wait up to 0.3 seconds for the target to read the release; a target busier than that still returns success (a failure would make the model retry and click twice), the helper result carries `read_confirmed: false`, and the success message adds that the input was sent and the target may still process it, so take a screenshot before repeating. After the release is read it is only briefly confirmed, so if the target opens a new window asynchronously later the result may not say the foreground changed. Scrolls and moves wait a fixed 300 ms after sending and do not wait for the target to read them.
- Screenshots on Windows 10 1903 to 1909 include the mouse cursor (2004 and newer do not, see the start of this guide).
- When only a dialog appears, `computer_launch_app` waits the full 10 seconds before returning it; when an app first opens an ownerless window (for example its own splash screen) it is taken as the main window. An `app_id` of the `shell:` form is started through the executable it points to, without the arguments in the shortcut; one that does not point to a program cannot be started.
- When the target hangs for more than 4 seconds the system may reset the keyboard state, and `computer_press_key` can return success before the key was read.
- When a key combination is another program's registered global hotkey, the keys go to that program (which may already have run its action) and the target does not read them; `computer_press_key` returns `input_failed` within about 1 second saying a hotkey may have intercepted them. A hotkey intercepted by a keyboard hook is not recognized and only fails at the 5-second limit.
- When the target is too busy to read a key combination within 5 seconds, `computer_press_key` returns `input_failed`, but the helper keeps waiting in the background for up to 30 seconds after the request so a key the target reads late still carries its modifiers; that wait ends when the next input action starts (after waiting at most 0.5 seconds first), and a key read after that may arrive without its modifiers.
- Typing and key presses to UWP apps only confirm that the app responded, not that it read the input; the keys can run one character ahead of the app, and when the app opens a new window because of the previous character, that character goes to the new window. The success message asks the model to confirm with a screenshot.
- Background delivery uses UI Automation only: web content, custom-drawn canvases and terminals usually have no usable pattern and return `background_unavailable`, leaving the model to decide whether to use the foreground. Invoke is not a real click, and a few apps only act on mouse events, in which case UI Automation reports success but nothing changes on screen, so a screenshot is needed to confirm.
- Foreground restore is "grabbed, then pulled back": between the target taking the foreground (about 2 to 9 ms) and being pulled back, a single key the user happens to type still reaches the target, and only preventing the target from grabbing the foreground would avoid that. That is why a background action first waits for the user to stop typing; typing continuously past the 3-second wait limit still runs the action.
- The zero-movement mouse move sent when a foreground restore is refused does not move the cursor, and the idle detection ignores injected input, but the window still receives one `WM_MOUSEMOVE`.
- Immediate restore can occasionally leave a Win32 check box's Toggle without effect (2 times in about 31 full test runs; it could not be reproduced in isolation); the result honestly reports that the state did not change, and the model can redo it.
- When the user's foreground window cannot be activated (`WS_EX_NOACTIVATE`) and the mouse is moving during the action, the asynchronous reorder may not take effect and the target stays directly below the foreground window; this case is not part of the stacking-order guarantee (see ADR 0002; the cause is tracked as a separate follow-up).

## Tests

```powershell
npm test
npm run test:rust
```

Tests that send real input or take screenshots only target this project's own test windows: fixed windows whose title starts with `CUMCP_`, the dialogs they open, and the topmost windows used to test covering. Tests of the approval dialog use the test tool `prompt-answerer` (it runs only in tests and is not shipped in the package), which clicks buttons or presses Enter like a person; the helper itself has no parameter or method that answers or skips a dialog. Before sending, the tests confirm that the foreground is one of those windows; failing to foreground counts as a test failure, not a skip. Keep the screen unlocked and do not touch the mouse or keyboard while the tests run.

`npm test` points `LOCALAPPDATA` at a temporary folder in every test process (`test/isolate-localappdata.mjs`) and deletes it at the end, so even a test that forgot to name its own folder cannot write logs, locks or grants into your `%LOCALAPPDATA%\deskpass`; the real path is kept in `COMPUTER_USE_TEST_REAL_LOCALAPPDATA`. When you run a single file directly with `node --test`, add `--import ./test/isolate-localappdata.mjs`.

The tests of the confirm window ("Deskpass confirmation") likewise use `prompt-answerer` to click the buttons (`--class DESKPASS_CONFIRM_CHANGE`). The Rust tests that depend on the foreground sometimes fail in a full run because they cannot get the foreground; run the failing one on its own again. Do not run `npm test` and `npm run test:rust` at the same time.

Continuous integration (`.github/workflows/ci.yml`) has no interactive desktop. It builds the TypeScript, builds the helper and its test binaries (`cargo test --no-run`, so every Rust integration test must still compile), runs the Rust unit tests (`cargo test --bins`), and runs `npm test` with `DESKPASS_NO_DESKTOP=1`, which skips the end-to-end and desktop tests that open real windows. The desktop tests (`helper/tests`, and the end-to-end tests in `test/e2e.test.ts`) run on a real desktop, by hand. [CONTRIBUTING](../CONTRIBUTING.md) has the checklist.

## Folders

All runtime data is in `%LOCALAPPDATA%\deskpass` (a temporary folder in tests):

- `session.lock`: the single-operator lock (see "Approval, risk tiers and the lock").
- `grants.json`, `grants.key`: the grants file and its key (see "Grants file").
- `settings.json`: the plain settings; today only `allow_background` (see "Background delivery and `delivery_mode`").
- `settings.lock`: the settings server's lock (see "Settings page (technical)").
- `logs\YYYY-MM-DD.jsonl`: the log (see "Log").

The program files of the package are in `%LOCALAPPDATA%\Programs\Deskpass`, apart from the data: install, upgrade and a normal uninstall do not touch the data. `%LOCALAPPDATA%\computer-use-mcp`, the old name of the development version, is not read, moved or deleted; `uninstall.ps1` refuses to delete any path that contains `computer-use-mcp`.

## Packaging

```powershell
npm run build
npm run package
```

`npm run package` (`scripts/package.mjs`) produces `release/deskpass-<version>.zip` (the version comes from `package.json`). It does not build the helper (cargo is slow, and it needs Rust and the C++ tools); it uses `dist/deskpass-helper.exe`, and refuses to package when that file is missing, when its reported build id does not match `dist/helper-build.json`, or when it is older than the sources in `helper/`; run `npm run build` first. The zip holds:

- `dist/`: `index.js`, `deskpass-helper.exe`, `helper-build.json`. `index.js` is one file bundled from `src/` by esbuild (an ES module with `@modelcontextprotocol/sdk` and `zod` bundled in, no source map, not minified, so error stacks stay readable); the settings page and the approval windows run from this file, and there is no other `.js` in `dist`;
- no `node_modules`: the runtime dependencies are bundled into `dist/index.js`, so installing copies only a few files;
- `package.json` (only the fields needed at run time, `"type": "module"` kept, no `dependencies`);
- `install.ps1`, `uninstall.ps1`, `deskpass-settings.vbs` (from `packaging/`);
- `README.md` and `VERSION`.

Packaging first type-checks with `tsc --noEmit`, then bundles; `npm ci` is not needed. When upgrading from an older version that had `node_modules`, `install.ps1` removes the old `node_modules` and `node_modules.old-*` in the install folder (failing to delete them is not a failure).

The zip is written by Windows' built-in `tar.exe`, or by `Compress-Archive` when that is missing. After changing the README, package again so the zip holds the new one. `-SkipShellIntegration` of `install.ps1` and `uninstall.ps1` is for tests only (it registers nothing and creates no shortcut); together with `LOCALAPPDATA` pointed at a temporary folder it lets you test copying and upgrading without touching your own settings.

What `install.ps1` does besides copying: it registers `deskpass` with Claude Code at user scope when `claude` is on PATH, prints the MCP server definition for this install (a JSON `mcpServers` block with `command` `node` and the installed `dist\index.js`) and copies it to the clipboard whether or not `claude` was found (a clipboard that cannot be written only warns), creates the Start menu shortcut (named "Deskpass Settings" in English, and in Traditional Chinese by the language rule above), and finishes by telling the user to restart their AI client. The messages of both scripts are tables of the same keys per language at the top of each script.

The package is not code-signed, and it is not published to npm (`package.json` is `private: true`). Releases carry the zip and its SHA-256 on GitHub Releases; the user guide tells users how to check it.
