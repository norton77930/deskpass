# Background delivery is implemented by foreground restore: when an app grabs the foreground, put it back immediately

ADR 0001 assumed that UIA actions do not need the foreground. Measurement showed this is false. The UIA proxy for standard Win32 controls calls SetForegroundWindow on the control from the client side. XAML apps (Calculator, Settings) and Chromium (Edge) bring themselves to the foreground during invoke, select, expand and SetValue even when the client has no foreground rights, so the client cannot prevent it. We decided that background delivery still uses UIA, but the helper watches the foreground before and after the action. If the target app's process (or the frame hosting it) takes the foreground between the start of the action and 500 ms after it returns, the helper immediately gives the foreground back to the window that had it before the action, and then asynchronously puts the target back at its original place in the window stacking order. Before each background action, Deskpass waits until the user's keyboard has been idle for 300 ms and no mouse button is held (for at most 3 seconds), and then acts. Only physical input counts: injected keys and clicks, including the AI's own foreground delivery, do not, which is the same principle the stop key uses. The wait is recorded in the result and the log (`waited_for_idle_ms`); if the full 3 seconds elapse and the action runs anyway, the log notes that idleness was never reached.

**Status:** accepted (2026-11-02, agreed in a design discussion). Partly supersedes ADR 0001: it replaces only the premise that "UIA actions do not need the foreground"; the decisions in 0001 about tool scope, `background_unavailable`, the border and the stop key stand.

## Evidence

A throwaway measurement: Notepad in the foreground, auto-typing one character about every 15 ms, while a UIA Invoke was sent to Calculator. Without restoring, about 73 of 95 characters went to the wrong window. Restoring only after the action returned took about 170 ms and still misdirected 11 characters. Restoring as soon as the `EVENT_SYSTEM_FOREGROUND` event arrived left the target in the foreground for only 2-9 ms and misdirected 0-3 characters. The user watched side by side over 5 runs and saw no flicker.

## Considered Options

- **Narrow background delivery to Win32 controls and use direct messages (`BM_CLICK` and similar)**: not adopted this time. It is safe, but modern apps (XAML, Chromium, Electron) could then only be operated in the foreground, which defeats the main scenario of the user and the AI using the computer at the same time. Direct messages are a second-phase improvement that could stop Win32 controls from jumping to the foreground even for a few milliseconds.
- **Restore only after the action returns**: rejected. The foreground is occupied for about 170 ms and typing visibly goes to the wrong place.
- **Shelve background delivery**: rejected. The experiment showed foreground restore is workable and the user sees no flicker.

## Consequences

- The guarantee of "background delivery" changes from "never steals the foreground" to "if the foreground is stolen, it is restored immediately". For a very short time the user's keystrokes can still reach the target app, which is why Deskpass waits for keyboard idleness before acting.
- A new window opened by a background action (for example a dialog) is also not left in the foreground; the AI's next step receives `dialog_open` under the existing rules.
- When restore succeeds, the result carries `foreground_restored: true`. When it fails, the action still counts as completed and returns `foreground_changed` with `restore_failed: true`, with no retry. Both are written to the log.
- The effect of modifier keys being split across two windows during restore is, in the first phase, only observed during manual acceptance.
- Implementation details (settled after the measurements, revised later): call `SetForegroundWindow` directly first; if it is refused, send a zero-movement mouse move with `SendInput` and try again. Do not attach thread input: attaching the user's thread drops what the user is typing, and attaching only one side keeps being refused. A single key typed at the moment of the grab still reaches the target. Whether a restore failed is judged from the foreground at the end of monitoring, not from the return value. The foreground is polled every 1 ms, because the foreground event arrives earlier than the foreground actually changes.
- Known limitation: restoring immediately can occasionally leave a Win32 checkbox Toggle without effect (2 failures in about 31 full test runs). The suspected cause is that the target is deactivated before it has processed the click UIA sent; it could not be reproduced in isolation. The result honestly reports that the state did not change, so the model can redo the action. The user chose to keep immediate restore, and the cause is tracked as a separate follow-up investigation.
- Known limitation: when the user's foreground window cannot be activated (WS_EX_NOACTIVATE) and the mouse is moving during the action, the asynchronous reorder may not take effect and the target stays in the window stack directly below the foreground window. The approaches that would fix the stacking order (a synchronous reorder, or reordering while input is attached) would make the foreground restore of the next action fail. Real user windows are all activatable, and 20 runs with an ordinary window did not reproduce it, so the user decided (2026-11-02) that this case is not covered by the stacking-order guarantee; the cause is tracked as a separate follow-up investigation.
